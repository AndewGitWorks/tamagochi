# CRUD backend

Добавлены модели, интерфейсы хранилищ, PostgreSQL-репозитории и HTTP-маршруты
для товаров, изображений, профилей, заказов, позиций заказа и избранного.
Готовый CRUD пользователей сохранён: добавлены список и маршруты текущего пользователя.
Используются `database/sql`, `context.Context` и явные SQL-запросы, как в `postgres_users.go`.
Новых зависимостей в `go.mod` нет. Клиент React не менялся.

## Запуск

Требуются Go 1.22+, Docker и Docker Compose. Из корня проекта:

```bash
cp .env.example .env
# Укажите свои POSTGRES_PASSWORD и JWT_SECRET в .env.
# JWT_SECRET должен содержать минимум 32 символа.
make env-up COMPOSE='docker compose'
make migrate-up COMPOSE='docker compose'
cd backend
go run ./cmd/api
```

`make migrate-up` запрашивает подтверждение применения миграций.
Миграция `000001_init` предназначена для **пустой базы**: она создаёт схему
`tamagochi` и все таблицы, включая `refresh_sessions` для существующей авторизации.
Если схема уже создана вручную, согласуйте её с миграцией перед применением.
Миграция вниз удаляет таблицы вместе с данными; для обычного запуска она не нужна.
Из `.gitignore` убрана строка `migrations`, чтобы миграции попадали в Git.

Старые SQL-примеры в `DOCS/Database` оставлены как документация исходного проекта.
Исполняемый SQL находится в `migrations`.

## Доступ

Публичны только чтение товаров и изображений, регистрация и вход.
Для остальных запросов передавайте `Authorization: Bearer <access_token>`.
Refresh-токен не подходит для CRUD; он используется только на `/refresh`.
Роль и существование пользователя проверяются в базе при каждом защищённом запросе.

Пользователь работает со своим аккаунтом, профилем, избранным и заказами.
Администратор дополнительно меняет каталог, читает список пользователей,
может открыть заказ по ID и изменить его статус.
`GET /orders` возвращает собственные заказы даже для администратора.
Регистрация всегда создаёт роль `USER`. Администратор назначается ответственным
за базу, например:

```sql
UPDATE tamagochi.users SET role = 'ADMIN' WHERE login = 'your_admin_login';
```

## Маршруты

`PUT` полностью заменяет изменяемые поля сущности. ID и связи задаются путём
запроса либо определяются по access-токену. Не передавайте их в JSON.
Создание возвращает `201`, чтение и изменение — `200`, удаление — `204` без тела.
Ошибки: `400` — данные, `401` — авторизация, `403` — права, `404` — запись
не найдена, `409` — конфликт, связь с другой записью или закрытый для правок заказ.

| Сущность | Создание | Чтение | Изменение | Удаление |
| --- | --- | --- | --- | --- |
| Пользователь | `POST /register` | `GET /users/me`, `GET /users` (ADMIN) | `PUT /users/me` | `DELETE /users/me` |
| Профиль | `POST /profiles/me` | `GET /profiles/me` | `PUT /profiles/me` | `DELETE /profiles/me` |
| Товар | `POST /products` | `GET /products`, `GET /products/{id}` | `PUT /products/{id}` | `DELETE /products/{id}` |
| Изображение товара | `POST /products/{productID}/images` | `GET /products/{productID}/images`, `GET /products/{productID}/images/{id}` | `PUT /products/{productID}/images/{id}` | `DELETE /products/{productID}/images/{id}` |
| Заказ | `POST /orders` | `GET /orders`, `GET /orders/{orderID}` | `PUT /orders/{orderID}` | `DELETE /orders/{orderID}` |
| Позиция заказа | `POST /orders/{orderID}/items` | `GET /orders/{orderID}/items`, `GET /orders/{orderID}/items/{id}` | `PUT /orders/{orderID}/items/{id}` | `DELETE /orders/{orderID}/items/{id}` |
| Избранное | `POST /likes/{productID}` | `GET /likes`, `GET /likes/{productID}` | Не требуется | `DELETE /likes/{productID}` |

Все списки поддерживают `?limit=20&offset=0`. `limit`: 1–100, `offset`: от 0.
Ответ списка — массив, в том числе `[]`, если записей нет.

## Примеры тел запросов

Товар: цена передаётся **строкой**, чтобы не терять точность при работе с деньгами.
Допустимо от `"0"` до `"99999999.99"`, максимум два знака после точки.
При отсутствии `seria_title` используется `NEWBIE`, `specifications` — `null`.

```json
{
  "title": "Tamagotchi Original",
  "price": "2490.00",
  "seria_title": "ORIGINAL",
  "bio": "Карманный питомец",
  "description": "Описание товара",
  "specifications": {"color": "blue", "battery": "CR2032"}
}
```

Изображение — это запись с ключом хранилища, загрузка самого файла не реализована:

```json
{"storage_key":"products/1/front.png","sort_order":0}
```

Профиль:

```json
{"bio":"О себе","address":"Адрес доставки"}
```

Профиль уже создаётся при регистрации. `POST /profiles/me` нужен для его
восстановления после удаления; повторное создание существующего профиля даёт `409`.
`orders_count` вычисляется из заказов при чтении, создании и изменении профиля,
а не принимается от клиента. Старый столбец сохранён для совместимости со схемой.

Пользователь — те же поля, что при регистрации. Пароль можно не передавать:

```json
{
  "login":"maria",
  "name":"Мария",
  "surname":"Иванова",
  "email":"maria@example.com",
  "phone_number":"+79991234567"
}
```

Новый пароль передаётся в `password`, хешируется на сервере и не возвращается.
`role`, `version` и `password_hashed` в JSON не принимаются.
После изменения логина нужно войти заново.
Удаление аккаунта, у которого остались заказы, запрещено внешним ключом (`409`).

Создание заказа: `{}`. Сервер назначает номер, владельца, `PENDING` и нулевую сумму.
После этого добавьте позиции:

```json
{"product_id":1,"quantity":2}
```

Цена берётся из товара на момент добавления. Позднейшее изменение цены товара
не меняет старую позицию заказа. Повторный товар в одном заказе даёт `409`:
обновите количество существующей позиции.
Изменение позиции принимает только количество:

```json
{"quantity":3}
```

Изменение заказа принимает статус:

```json
{"status":"CANCELLED"}
```

Владелец может только отменить `PENDING`-заказ. Администратор может установить
`PENDING`, `PAID`, `PAYMENT_FAILED`, `DELIVERING`, `DELIVERED`, `CANCELLED`.
Это ручной CRUD статуса; интеграции с оплатой и доставкой здесь нет.
Позиции можно менять только в `PENDING`. Их изменение и пересчёт общей суммы
выполняются в одной транзакции с блокировкой строки заказа.
Удаление заказа разрешено для `PENDING` и `CANCELLED` и удаляет его позиции.
Товар, который есть в позиции заказа, удалить нельзя (`409`).
Изображения и избранное удаляются автоматически вместе с товаром.

Для добавления в избранное тело запроса не требуется. Изменение связи не нужно:
у неё только ключ `(user_id, product_id)` и время создания.

## Быстрая проверка запросами

Получите access-токен через существующий `POST /login` или `POST /register`.
Для изменения каталога нужен токен пользователя с ролью `ADMIN`.

```bash
export TOKEN='access_token_here'
curl -H "Authorization: Bearer $TOKEN" \
  -H 'Content-Type: application/json' \
  -d '{"title":"Tamagotchi Original","price":"2490.00"}' \
  http://localhost:8080/products
curl 'http://localhost:8080/products?limit=20&offset=0'
curl -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
  -d '{}' http://localhost:8080/orders
# Подставьте ID созданного заказа и товара:
curl -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
  -d '{"product_id":1,"quantity":2}' http://localhost:8080/orders/1/items
curl -H "Authorization: Bearer $TOKEN" http://localhost:8080/orders/1
```

## Тесты

```bash
cd backend
go test ./...
go vet ./...
# На отдельной тестовой базе с применённой миграцией:
TEST_DATABASE_URL='postgres://user:password@localhost:5432/tamagochi_test?sslmode=disable' go test -count=1 ./...
```

Без `TEST_DATABASE_URL` интеграционные тесты пропускаются. Интеграционный тест
проверяет все новые репозитории, десятичные цены, сохранение цены позиции,
пересчёт суммы, запрет редактирования оплаченного заказа, счётчик заказов,
связи и каскадные удаления. Тест создаёт собственные записи и убирает их за собой.
HTTP-тесты проверяют права администратора, отказ refresh-токену, защиту чужого
заказа, закрытые поля JSON и отсутствие хеша пароля в ответах.

Проверка этой версии: `go test ./...` и `go vet ./...` прошли на Go 1.22.12.
Интеграционные тесты и миграции `up → down → up` прошли на встроенном PostgreSQL
(PGlite) через тот же драйвер pgx; для тестового соединения использовался
`default_query_exec_mode=simple_protocol`. Этот параметр в приложение не добавлен.
Отдельный PostgreSQL 18 из Docker Compose в этой среде не запускался;
конкурентные транзакции следует дополнительно проверять на обычном PostgreSQL.
